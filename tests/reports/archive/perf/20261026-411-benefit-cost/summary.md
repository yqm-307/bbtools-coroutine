# #411 R4：收益与代价核对结论

## 结论

R4 省的是事件就绪后等待下一扫描拍的墙上时间，不是减少业务操作。
io/1 的吞吐和尾延迟明显改善，但单位操作 CPU 确实退化。值得继续保留推进，不因 RISK 自动否决；尚未证实新增 CPU 花在哪个函数，不声称根因已闭环。

本次只读既有 57 样本、候选 diff、驱动及 Boost 实现，新增性能采样 0、测试 0、产品改动 0。仍未提交、未合并。

## 前后时序

```text
旧：协程 read 遇到等待 → 挂起并登记事件
    S线程非阻塞排空 → 定时休眠 ── FD就绪但不能打断sleep ── 下一拍poll → 唤醒P → 恢复协程
新：协程 read 遇到等待 → 挂起并登记事件
    S线程非阻塞排空 → run_one_until(deadline) ── 已监听FD就绪 → 派发 → 唤醒P → 恢复协程
                                                   └→ 再进_OnUpdate排空/维护
```

- 默认扫描间隔 1ms（候选 `bbt/coroutine/detail/GlobalConfig.hpp:49`），不是每个请求固定损失或至少损失 1ms；sleep 只在排空后发生，额外等待取决于事件到达时机，OS 调度还会影响实际延迟。
- `Scheduler.cc:580-599`：事件提前醒来不推远扫描 deadline；无事件退回定时休眠。
- `CoPoller.cc:89-113`、`CoPoller.hpp:58-65`：等待有上界；开始等待后首次登记的新 FD 不保证立即打断，最迟由 deadline 收敛。
- R4 没有新增线程，也没有减少 payload 校验、I/O 收发等业务步骤。

## CPU 到底贵在哪里

### 已确认：总CPU和单位CPU是两笔账

取 io/1 第2轮的同轮真实值，不拼接独立中位数：

- base：81,851 次往返，1.509529 CPU秒，平均占用约 0.189 核。
- candidate：528,433 次往返，12.739829 CPU秒，平均占用约 1.592 核。
- 按基线每操作成本分账：新增CPU约 73.34%对应多完成操作，26.66%对应候选每操作更贵。其余两轮约 72.47%/27.53%、72.58%/27.42%。
- 分账公式：`ΔCPU = (N1−N0)×U0 + N1×(U1−U0)`。这是以基线成本为参照的算术分解，改变分解次序会改变份额，不能当作线程或函数热点占比。
- 不能说CPU增加全是多干活，也不能说这不是退化：单位CPU上升是真实取舍。

### 代码可见、但成本尚未隔离

`run_one_until` 派发一个事件后回到 `_OnUpdate`。后者（`Scheduler.cc:527-556`）执行 `_AutoScaleTick`、`_ReapRetiredWorkers`、非阻塞poll、`_FixTimingScan`、栈池OnUpdate。即便个别方法内部按时间/配置提前返回，这些入口检查仍会被调用。

因此，较早且较频繁地处理事件可能增加扫描、维护检查、线程交接，也可能改变原有批量摊销。这比只盯新增 guard/restart 更完整，但仍是待证实的成本方向。

`work_guard`、`restart`、`run_one_until` 也是待定位路径，不是已证实热点。原非阻塞 `EventLoop.cc:36-40` 已调用 `restart`。Boost 的 `executor_work_guard.hpp:97-123` 为内联对象及work记账，不能据创建销毁就声称每次堆分配。

没有本次线程、函数、系统调用采样，不能断定S线程占了新增CPU多少，也不能证明忙等或通知风暴。不能建议先移除正确性保护来追求CPU指标。

## 单/双 worker 与场景边界

- workers=1 只限制执行协程的P线程数，另有S调度线程及主线程；不是全进程只有一个线程。
- 驱动是本地UNIX socketpair、64B、16路闭环请求/响应、8秒活动窗加排空，不是真实TCP服务。
- `perf_spotcheck.cc:310-356` 的P99含客户端发起、server处理、往返等待、协程调度与校验，不是内核ready→Resume的单阶段延迟。
- `ProcessCpu` 使用 `getrusage(RUSAGE_SELF)`，覆盖进程所有线程user+system CPU；`RunPhase:405-421` 包含排空阶段。
- 16并发下 `1/ops` 不是单请求平均延迟，不能把96μs→15μs解释为已测平均往返延迟。
- io/2基线本就更快，worker交错运行可能减少落入停拍的影响；仅凭吞吐差异不能证明掩盖比例，也不能说CPU被并发自动摊薄。io/2逐轮单位CPU变化有波动，详见原报告。
- 更可能受益的是频繁挂起、I/O就绪延迟敏感且有CPU余量的负载；这是机制推断，不是生产认证。CPU已饱和/功耗预算严格的负载需留意单位CPU代价。
- 不应断言单worker不适合：它恰好展示最大吞吐收益。也不能据spawn/chan结果断言CPU密集型业务退化。
- 既有5秒idle CPU：base 60.560ms、candidate 55.478ms，单次样本不支持精确改善认证，但也不能据此声称R4导致空闲忙等。与Go的基础差距不等于R4引入的差距。
- 未测固定到达率/同吞吐下CPU、真实网络/业务处理、跨平台、分配次数、锁和切换次数，不外推。
